У рамках виконання даної роботи було проведено комплексний аналіз та підготовку до розробки програмної системи для попереднього замовлення їжі та напоїв. Основним завданням цього етапу було формування чіткого бачення продукту, визначення його меж та технічних вимог.
Результатом цього етапу став деталізований документ «Концепція та рамки проєкту» (Vision & Scope), який наведено у Додатку Б.

2. Сформульовано призначення майбутньої системи, її унікальну цінність для клієнтів та закладів харчування (розділ 2.1 Додатку Б).
3. Детально описано бізнес-логіку взаємодії всіх сторін: від первинного налаштування закладу до моменту видачі замовлення клієнту (розділ 2.2 Додатку Б).
4. Визначено технічні та функціональні рамки проєкту, включаючи вимоги до серверної частини, кухонного IoT-клієнта, веб-панелі адміністратора та мобільного додатку (розділи 3.1, 3.2 Додатку Б).
5. Сформовано та обґрунтовано повний технологічний стек (мови програмування, фреймворки, СУБД, інструменти), який буде використано для реалізації всіх компонентів системи (розділ 4.3 Додатку Б).
Створений документ (Додаток Б) є фундаментальною основою для подальших етапів проєктування архітектури, безпосередньої розробки та подальшого тестування програмного продукту.

VISION AND SCOPE DOCUMENT (КОНЦЕПЦІЯ ТА РАМКИ ПРОЄКТУ) 

1 BUSINESS REQUIREMENTS (БІЗНЕС-ВИМОГИ)

1.1 Аналіз проблеми
Наразі у світі, час є одним з найцінніших ресурсів як для споживачів, так і для бізнесу. Процес замовлення їжі та напоїв у популярних закладах, особливо в години пікового навантаження, як-от ранкові години чи обідні перерви, нерозривно пов'язаний з очікуванням у чергах та неефективною витратою цього цінного ресурсу. Цей проєкт спрямований на розробку програмної системи для попереднього замовлення, яка пропонує зручне та сучасне рішення цієї ключової проблеми. Основний акцент робиться на усуненні бар'єрів та вирішенні проблеми неефективності та втрати часу в закладах громадського харчування.
Для клієнтів харчових закладів основна проблема полягає у вимушеному очікуванні: спочатку в черзі, щоб зробити замовлення, а потім в очікуванні його приготування. Для самих закладів проблема полягає в ускладненому керуванні потоком клієнтів. Довгі черги можуть відлякувати потенційних покупців, які не готові чекати, що призводить до прямої втрати прибутку. Крім того, персонал витрачає значний час на рутинні операції прийому замовлень та проведення оплат, які можна було б автоматизувати.
Важливість вирішення цієї проблеми є досить очевидною. Для клієнтів - це можливість заощадити в середньому 10-20 хвилин вільного часу щодня. Для закладів це потужний інструмент підвищення конкурентоспроможності: система дозволяє збільшити пропускну здатність без фізичного розширення, підвищити лояльність клієнтів.
Існуючі підходи не задовольняють цю потребу повною мірою, тому що, наприклад, традиційні замовленні на місці є першопричиною черг та непередбачуваного часу очікування споживача закладу; замовлення по телефону, хоч і є кроком уперед, але персонал може бути перевантаженим і не зможе відповісти на дзвінок, що спричиняє вищу вірогідність втратити потенційного клієнта, а також існуючі системи доставки (наприклад, Glovo, Bolt Food) орієнтовані на логістику доставки, а не на оптимізацію процесу самовивозу.
Таким чином, розробка програмної системи для попереднього замовлення є прямою відповіддю на існуючий ринковий попит, який не задовольняється у повній мірі поточними рішеннями.

1.2 Аналіз аналогів
Зараз на ринку існують кілька рішень, які частково перекривають функціонал системи попереднього замовлення. Їх можна розглядати як непрямих конкурентів та аналоги, чиї недоліки створюють можливість для нашого продукту. Під час аналізу існуючих аналогів було виділено щонайменше 3 аналоги спроб вирішення поточної проблеми попереднього замовлення, а саме: по-перше, системи доставки (Glovo, Bolt Food), які об'єднують тисячі закладів. Їхня основна бізнес-модель - це доставка замовлень кур'єрами. Функція самовивозу ("Pickup") є вторинною, що саме і є вагомим недоліком, оскільки вся їхня економічна та технологічна модель побудована навколо логістики доставки, а не попереднього замовлення; по-друге, це власні мобільні додатки великих мереж (McDonald's, Starbucks). Їхні проблеми полягають в тому, що висока вартість розробки та підтримки лише свого додатку робить цю технологію недоступною для малого та середнього бізнесу. Це створює ринок, де сучасні інструменти є привілеєм лише для найбільших гравців, що закриває для іншої частини бізнес-ринку великі можливості; по-третє, індивідуальні сторінки замовлень, які заклади створюють через сервіси на кшталт Poster чи Choice QR. Їхня головна проблема для попереднього замовлення - незручність та фрагментованість. Клієнт щоразу змушений шукати окреме посилання на меню, а відсутність єдиного додатку та профілю унеможливлює збереження історії, швидке повторення замовлень та участь у програмах лояльності.
Наша система розроблена як пряма та цільова відповідь на недоліки існуючих аналогів, щоб зайняти унікальну ринкову нішу. Вона покращить ситуацію, створивши єдину, зручну та вигідну екосистему як для клієнтів, так і для закладів. На відміну від фрагментованих рішень (власні додатки мереж чи окремі сайти), ідея полягає у розробці єдиної платформи. Для користувача це означає фундаментальне покращення досвіду: замість завантаження десятків програм для кожної кав'ярні, він отримує один додаток з єдиним профілем та історією замовлень. Це забезпечує максимальну швидкість: "зайшов - вибрав заклад поруч - замовив". Для бізнесу система зрівняє доступ до технологій, надаючи і малим закладам “доступ” до інструментів рівня великих корпорацій (мобільний додаток, IoT-клієнт, CRM).
Ключовою відмінністю від сервісів доставки стане вигідна бізнес-модель (SaaS). Ми замінюємо високі комісії з кожного чека на фіксовану абонплату. Це дозволяє закладам не завищувати ціни в додатку, тож користувач купує їжу за реальною вартістю меню, що робить сервіс фінансово привабливим для щоденного використання студентами та офісними працівниками.»

2 VISION OF THE SOLUTION (КОНЦЕПЦІЯ РІШЕННЯ)

2.1 Опис призначення системи
Програмна система виступає своєрідним містком між щоденним плануванням людини та фізичним світом закладів харчування. Вона перетворює рутинну задачу, як-от купівля кави чи обіду, з процесу очікування на одну плавну та передбачувану дію. Користувач отримує можливість вписати візит до улюбленого закладу у свій щільний графік, роблячи його надійною точкою на маршруті, а не потенційною затримкою, що є наразі.
Для бізнес-партнерів система створює керований та організований потік передплачених замовлень. Це дозволяє їм ефективніше керувати завантаженістю кухні та персоналу, згладжуючи пікові навантаження. Замість хаотичних черг заклад отримує стабільний потік клієнтів, які приходять за вже готовими замовленнями, що робить операційні процеси більш спокійними та продуктивними.
Основна цінність для клієнта полягає у контролі над своїм часом. Система усуває тривожність "а що, як буде черга?", перетворюючи звичайну транзакцію на гарантовано швидку та приємну взаємодію. Йдеться про те, щоб сервіси міста працювали за графіком користувача, надаючи йому впевненість та комфорт у повсякденних справах.
Для закладів цінність полягає у виході на новий рівень ефективності та зміцненні зв'язку з клієнтами. Система перетворює їх із суто офлайн-точки на сучасний, цифровий бізнес, доступний для замовлення в будь-який момент. Це не просто збільшує пропускну здатність і дохід, а й будує лояльність сучасної аудиторії.

2.2 Опис бізнес-логіки
Робота системи будується на чіткій та зрозумілій взаємодії трьох сторін: власника закладу, клієнта та працівників кухні. Весь процес організований як безперервний потік, який починається з підготовки закладу до роботи. Власник або менеджер спочатку реєструється в адмін-панелі та створює "акаунт" свого закладу. Він вносить базову інформацію, таку як адреса й графік, але найголовніше формує меню. Він додає фотографії страв, описи та ціни, щоб клієнт бачив привабливу картинку. Також на цьому етапі підключається система онлайн-оплат та налаштовується кухонний екран (IoT-клієнт). Тільки після цього заклад з'являється в додатку і готовий приймати замовлення.
Основна дія починається, коли клієнт відкриває застосунок. Він знаходить заклад на карті або у списку, обирає їжу та додає її в кошик. Важливим моментом є те, що клієнт сам обирає час, коли хотів би забрати замовлення, і обов'язково оплачує його онлайн прямо в додатку. Саме факт успішної оплати є сигналом для системи, що замовлення реальне. Це захищає заклад від ситуацій, коли їжу приготували, а клієнт не прийшов і не заплатив.
Як тільки оплата пройшла, замовлення миттєво з'являється на екрані у працівників закладу (на кухні чи біля бару). Персонал бачить, що саме треба приготувати і на котру годину. Вони приймають замовлення і починають готувати. Коли страва готова, працівник натискає кнопку на екрані, і клієнт одразу отримує повідомлення на телефон: "Можна забирати". Клієнт приходить у заклад, називає номер свого замовлення і просто забирає пакет. Йому не треба стояти в черзі до каси чи діставати гаманець, адже все вже оплачено.
Паралельно з цим менеджер закладу має повний контроль над ситуацією. Якщо на кухні закінчилося молоко чи певні продукти, він може за секунду приховати відповідні страви з меню через свою панель управління (поставити в "стоп-лист"), щоб клієнти не могли їх замовити помилково.

3 SCOPE AND LIMITATIONS (РАМКИ ТА ОБМЕЖЕННЯ ПРОЄКТУ) 

3.1 Опис функціональності серверної частини та IoT-клієнта
Серверна частина виступає центральним елементом системи, побудованої на базі RESTful API. Сервер відповідає за цілісність даних, виконання бізнес-правил та управлінням процесів між усіма клієнтськими додатками. Розглянемо детальніше завдання сервера:
* архітектура даних та медіа: управління реляційною базою даних (MSSQL) для зберігання структурованої інформації: профілів користувачів, ієрархії меню, історії транзакцій; робота з хмарним сховищем (Blob Storage) для оптимізованого зберігання медіа-контенту (фотографій страв, логотипів), розвантажуючи основну базу від "важких" файлів; забезпечення мультимовності на рівні моделі даних: видача контенту (назви, описи) відповідно до мовного заголовка запиту (EN/UA).
* управління доступом та безпека: реалізація механізму автентифікації на основі JWT-токенів для захисту сесій; контроль ролей (Role-Based Access Control).
* управління каталогом (меню): забезпечення CRUD-операцій для формування меню: створення категорій, прив’язка інгредієнтів, налаштування модифікаторів (наприклад, вибір розміру порції); миттєве блокування можливості замовлення страв у всіх клієнтів при отриманні сигналу про відсутність інгредієнтів.
* обробка життєвого циклу замовлення: валідація вхідних даних кошика (перевірка актуальності цін, наявності позицій); інтеграція з платіжним шлюзом: ініціалізація транзакції та зміна статусу замовлення лише після підтвердження успішної оплати; автоматичний розподіл вхідних заявок на конкретні IoT-термінали відповідних закладів.
* API та документування: надання документованих точок доступу (Swagger UI) для взаємодії з мобільними та веб-клієнтами.
IoT-клієнт - програмне забезпечення для планшетів, OLED-дисплеїв або терміналів у зоні приготування, яке замінює принтери чеків та забезпечує двосторонній зв'язок "Кухня ⇔ Сервер". Детальніше про функціональні завдання IoT-клієнта: 
   1. відображення черги замовлень у форматі інтерактивних карток.
   2. деталізація кожної картки: склад замовлення, коментарі клієнта, номер чека, ім'я замовника.
   3. відображення динамічного таймера для кожного замовлення з кольоровою індикацією критичного часу очікування.
   4. зміна статусів в один дотик: переведення замовлення зі статусу "Нове" в "Готується", а потім у "Готово до видачі".
   5. синхронізація статусів: відправка сигналу на сервер для автоматичної генерації push-сповіщення клієнту (наприклад, "Ваша кава готова").
   6. звукові та візуальні сповіщення персоналу про надходження нових замовлень.

3.2 Опис функціональності веб-клієнта та мобільного клієнта
Веб-клієнт та мобільний клієнт є двома основними точками входу для користувачів в екосистему, проте вони розроблені з різними пріоритетами та для дещо відмінних сценаріїв використання. Архітектурний фундамент взаємодії базується на використанні єдиного універсального RESTful API, що гарантує цілісність та миттєву синхронізацію даних між усіма платформами екосистеми.
Веб-клієнт розробляється на бібліотеці React як швидка та зручна панель управління для власників бізнесу. Він слугує єдиним центром для налаштування роботи закладу: від простої реєстрації та введення реквізитів до встановлення графіку роботи.
Ключовою функцією є управління меню. Через зрозумілий інтерфейс адміністратор створює категорії, додає страви, налаштовує ціни та завантажує фотографії, які система автоматично оптимізує для швидкого відображення. Також веб-клієнт надає доступ до аналітики, де у вигляді наочних графіків показано статистику продажів та пікові години навантаження. Безпека гарантується системою розмежування прав, що дозволяє надати різний рівень доступу для власника та найманого менеджера.
Мобільний додаток розробляється на платформі Flutter, що дозволяє створити швидкий та зручний сервіс одночасно для iOS та Android. Це основний інструмент для гостя, який починається з простої реєстрації через номер телефону або email.
Ключовою функцією є геолокація: додаток автоматично визначає місцезнаходження користувача, показує найближчі заклади на карті та сортує їх за відстанню. Вбудована платіжна система дозволяє безпечно платити в один дотик, зберігаючи дані картки для майбутніх покупок. Головна особливість - це живий зв'язок із кухнею: завдяки постійному з'єднанню клієнт отримує миттєві повідомлення про статус замовлення ("Готується", "Готово") прямо на екран, без необхідності постійно оновлювати додаток.

4 BUSINESS CONTEXT (БІЗНЕС-КОНТЕКСТ)

4.3 Опис програмних засобів та інструментів
Серверна архітектура реалізується на базі екосистеми Microsoft, використовуючи мову C# та платформу .NET (ASP.NET Core). Це забезпечує створення високопродуктивного RESTful API зі строгою типізацією. Для збереження структурованих даних обрано реляційну СУБД Microsoft SQL Server (MSSQL), яка нативно інтегрується з платформою через Entity Framework Core. Для оптимізованого зберігання медіа-контенту (зокрема фотографій страв) використовується хмарне сховище Azure Blob Storage, що розвантажує основну базу даних. Критично важливим елементом є використання технології SignalR, що дозволяє реалізувати двонаправлену комунікацію через WebSockets для миттєвої синхронізації замовлень між сервером, мобільним додатком та IoT-клієнтом. Документування API здійснюється автоматично через інструмент Swagger (OpenAPI), що спрощує взаємодію команд розробки.
Клієнтські частини системи розробляються з використанням сучасних компонентних підходів. Веб-клієнт (адміністративна панель та публічний сайт) створюється на бібліотеці React із використанням мови TypeScript. Це поєднання гарантує надійність коду та високу динаміку інтерфейсу, необхідну для управління складними бізнес-процесами. Мобільний клієнт реалізується на фреймворку Flutter (мова Dart). Вибір цієї технології дозволяє отримати нативну продуктивність та ідентичний користувацький досвід одночасно на iOS та Android, використовуючи єдину кодову базу, що значно оптимізує ресурси на розробку.
У ролі апаратної платформи для кухонного IoT-термінала використовується мікрокомп'ютер Raspberry Pi 4 (або новішої версії). Цей пристрій забезпечує достатню продуктивність для відображення графічного інтерфейсу на сенсорних дисплеях та підтримує стабільний бездротовий зв'язок із сервером.
Інфраструктура розробки побудована на використанні системи контролю версій Git, що є стандартом для командної роботи. Проєктування інтерфейсів (UI/UX) виконується у середовищі Figma. В якості інтегрованих середовищ розробки (IDE) обрано спеціалізовані інструменти: Visual Studio 2022 для роботи з серверною частиною та базами даних, і Visual Studio Code - легкий та потужний редактор для розробки фронтенду та мобільного додатку.
