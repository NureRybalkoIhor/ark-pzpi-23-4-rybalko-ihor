3 ОПИС ВИКОНАНОЇ РОБОТИ
Під час виконання лабораторної роботи було опрацьовано питання розробки бази даних для серверної частини програмної системи та прикладного програмного інтерфейсу (API). В основі серверної частини системи лежить платформа .NET 8 із використанням фреймворку ASP.NET Core Web API. Для організації кодової бази обрано багатошарову архітектуру (Clean Architecture), яка передбачає чіткий розподіл відповідальності між компонентами. Система розділена на незалежні шари: Domain (містить основні сутності та бізнес-правила), Application (відповідає за логіку обробки даних та DTO), Infrastructure (реалізує зовнішні сервіси, зокрема генерацію JWT-токенів) та Persistence (забезпечує безпосередню взаємодію з базою даних). Такий підхід дозволяє ізолювати бізнес-логіку від деталей реалізації інфраструктури та спрощує подальше тестування й підтримку програмного продукту. Взаємодія з клієнтськими застосунками реалізована за архітектурним стилем REST, де обмін даними відбувається у форматі JSON через стандартні HTTP-методи. Для забезпечення безпеки та розмежування доступу впроваджено механізм автентифікації на базі стандарту JWT (JSON Web Token).
Модель даних системи складається з низки взаємопов'язаних сутностей, що відображають предметну область. Сутність User представляє користувачів системи різних ролей, включаючи клієнтів, власників закладів та персонал, і містить дані для автентифікації. Сутність Restaurant описує конкретний заклад харчування, зберігає інформацію про його локацію, статус підписки та виступає кореневим елементом для меню та замовлень. Сутності Category та Dish формують ієрархічну структуру меню, де кожна страва належить до певної категорії. Процес обслуговування описується сутностями Order та OrderItem, де перша зберігає загальні дані про транзакцію, статус та час виконання, а друга деталізує склад замовлення з фіксацією ціни на момент покупки.
Зв'язки між моделями реалізовано переважно за типом "один-до-багатьох". Зокрема, один ресторан містить багато категорій, кожна категорія включає набір страв, а користувачі можуть створювати історію з багатьох замовлень. Також реалізовано специфічні зв'язки для функціонування апаратної частини системи: сутність IoTDevice, яка представляє кухонний термінал, має жорстку прив'язку до конкретного ресторану, що дозволяє авторизувати пристрої та розподіляти замовлення на відповідні кухні. Додаткові сутності Review та Notification забезпечують зворотний зв'язок та інформування користувачів про зміни станів їхніх замовлень. 
3.1 UML-діаграма прецедентів
На етапі проєктування поведінки системи було створено UML-діаграму прецедентів (рис. 2.1), яка визначає межі системи. Діаграма демонструє взаємодію між зовнішніми акторами (користувачами та пристроями) та прецедентами використання, що реалізовані у вигляді API-ендпоінтів.
Ієрархія користувачів побудована на принципі наслідування ролей, де базовим актором виступає «Гість». Цей актор представляє неавторизованого користувача, чия взаємодія з системою обмежена процесами ідентифікації, а саме реєстрацією нового облікового запису та проходженням автентифікації для отримання токена доступу.
Ключовим актором системи є «Клієнт», який успадковує базові права гостя та отримує доступ до основного бізнес-процесу. Сценарії використання клієнта охоплюють перегляд доступних ресторанів та їхніх меню, перегляд історії власних транзакцій, написання відгуків та отримання системних сповіщень. Центральним елементом взаємодії клієнта є прецедент «Оформлення попереднього замовлення». На діаграмі відображено складну структуру цього процесу через відношення включення («include»), яке вказує на обов'язковість виконання трьох підпроцесів: вказання часу самовивозу, що є критичною відмінністю системи попереднього замовлення від служб доставки, проведення онлайн-оплати для фіксації транзакції, а також автоматичного розрахунку вартості замовлення на стороні сервера.
Адміністративні функції виконує актор «Власник», який також успадковує базові можливості взаємодії з системою. До його компетенції належить створення профілю ресторану та управління його контентом через CRUD-операції з меню. Додатковою функцією власника є реєстрація IoT-терміналів, що забезпечує авторизований доступ кухонного обладнання до API системи.
Операційну діяльність закладу забезпечує актор «Працівник кухні / IoT», який взаємодіє із системою через спеціалізований термінал. Основний сценарій використання для цього актора полягає у моніторингу черги активних замовлень та управлінні їхнім життєвим циклом. Зміна статусу замовлення, наприклад переведення зі стану приготування у стан готовності, виступає тригером для внутрішньої логіки системи, що автоматично ініціює прецедент відправки сповіщення клієнту про готовність замовлення до видачі.

3.2 ER-діаграма (Entity-Relationship Diagram)
З метою формалізації структурування даних предметної області було спроєктовано ER-діаграму (Entity-Relationship Diagram) (рис. 2.2). Дана модель відображає логічну структуру бази даних, визначає набір необхідних сутностей, їхній склад атрибутів та характер зв'язків між ними.
Центральним елементом моделі виступає сутність User, яка містить інформацію про всіх учасників системи незалежно від їхньої ролі (клієнт, адміністратор, персонал). Атрибутивний склад цієї сутності включає ідентифікаційні дані, контактну інформацію та хешований пароль для забезпечення безпеки доступу. З сутністю користувача пов'язана сутність Restaurant, яка описує профіль закладу харчування. Між ними встановлено зв'язок типу «один-до-багатьох», що дозволяє одному власнику керувати мережею закладів. Ресторан виступає кореневим елементом для ієрархії меню, що реалізується через сутності Category та Dish. Категорії забезпечують логічне групування, а сутність страви містить детальні характеристики товару, включаючи ціну та час приготування.
Транзакційна логіка системи реалізована через взаємопов'язані сутності Order та OrderItem. Сутність Order представляє заголовок замовлення та містить ключові атрибути для бізнес-процесу попереднього замовлення: VisitTime (бажаний час візиту клієнта), EstimatedReadyTime (розрахунковий час готовності) та PaymentTransactionId (ідентифікатор транзакції платіжного шлюзу). Деталізація складу замовлення винесена в асоціативну сутність OrderItem, яка фіксує перелік страв та їхню вартість на момент створення замовлення.
Для забезпечення інтеграції з апаратною частиною комплексу в модель введено сутність IoTDevice. Вона містить унікальні ідентифікатори терміналів та має жорсткий зв'язок з конкретним рестораном, що дозволяє розмежовувати потоки замовлень між різними кухнями. Комунікаційні можливості системи та зворотний зв'язок реалізовано через допоміжні сутності Notification та Review. Перша забезпечує збереження історії сповіщень про зміну статусів замовлень, а друга збирає рейтинги та текстові коментарі користувачів щодо якості страв.
Усі зв'язки в діаграмі побудовані за принципом забезпечення посилальної цілісності даних. Переважним типом кардинальності зв'язків є «один-до-багатьох» (1:N). Наприклад, один користувач може мати безліч замовлень, один ресторан може мати безліч категорій, а одна категорія може мати безліч страв. Така нормалізована структура дозволяє уникнути дублювання інформації та забезпечує гнучкість системи при масштабуванні.

3.3 Розробка бази даних програмної системи
На основі побудованої ER-діаграми було виконано фізичне проєктування таблиць бази даних. Для забезпечення цілісності даних, усунення дублювання інформації було проведено процес нормалізації схеми даних, який складався з трьох послідовних етапів.
Вимоги 1NF передбачають, що всі атрибути таблиці мають бути атомарними (неподільними), а таблиця не повинна містити групи полів, що повторюються. На початковому етапі дані про замовлення могли б виглядати як єдина таблиця, де в одному рядку перераховано декілька страв. Для приведення до 1NF такі записи було розділено так, щоб кожен рядок містив інформацію лише про одну позицію замовлення.

	Вимоги 2NF передбачають, що таблиця повинна перебувати в 1NF, і всі неключові атрибути повинні залежати від повного первинного ключа. У таблиці з етапу 1NF спостерігалася часткова залежність: CustomerName залежав лише від ідентифікатора клієнта, а RestaurantAddress лише від ідентифікатора ресторану, а не від конкретного замовлення. Тому дані було розділено на окремі сутності: Users, Restaurants, Dishes. У таблиці замовлень залишилися лише посилання (зовнішні ключі).
Вимоги 3NF передбачають, що таблиця знаходиться в 2NF і не містить транзитивних залежностей (неключові атрибути не повинні залежати від інших неключових атрибутів). Наприклад, у таблиці Dishes зберігалася назва категорії (NameUA, NameEN). Це створювало транзитивну залежність, оскільки назва категорії залежить від ID категорії, а не від ID страви. Тому категорії було винесено в окрему таблицю Categories.
Таким чином, у результаті послідовного виконання процедур нормалізації було сформовано оптимізовану реляційну модель даних, приведену до 3NF. Це дозволило усунути надмірність та дублювання інформації, забезпечити посилальну цілісність даних та створити гнучку структуру бази даних, яка є стійкою до аномалій вставки, оновлення та видалення записів.
3.4 Створення діаграми структури БД
На основі попередньо розробленої нормалізованої моделі було спроєктовано детальну діаграму структури бази даних (рис. 2.3) (Physical Data Model). У рамках цього етапу було проведено специфікацію таблиць, визначено точні типи даних для кожного атрибута, встановлено необхідні обмеження на розмірність полів та зафіксовано ключові поля, що є необхідним для подальшої програмної реалізації.
З метою оптимізації зберігання даних та підвищення продуктивності системи було застосовано сувору типізацію рядкових атрибутів. Замість використання універсального, але ресурсомісткого типу NVARCHAR(MAX), для більшості текстових полів встановлено чіткі ліміти відповідно до бізнес-логіки: наприклад, NVARCHAR(100) для імен користувачів, NVARCHAR(50) для серійних номерів пристроїв та NVARCHAR(30) для електронних адрес. Такий підхід дозволяє суттєво зменшити фізичний обсяг бази даних та підвищити ефективність роботи індексів при пошукових запитах. Окрему увагу приділено точності розрахунків: для зберігання фінансових показників, зокрема полів ціни (Price) та загальної вартості (TotalAmount), використано тип DECIMAL(18,2). Це є загальноприйнятим стандартом для фінансових операцій, оскільки він запобігає похибкам округлення, які неминуче виникають при використанні типів із плаваючою комою.
Забезпечення логічної цілісності даних реалізовано через систему обмежень та ключів. Усі первинні ключі (PK) визначено з обов'язковим атрибутом NOT NULL, що гарантує наявність унікального ідентифікатора для кожного запису в системі та унеможливлює створення невизначених посилань. Структурна зв'язність між таблицями підтримується за допомогою механізму зовнішніх ключів (FK), які забезпечують посилальну цілісність (Referential Integrity). Це обмеження гарантує валідність даних, унеможливлюючи появу так званих «сирітських» записів, наприклад, створення замовлення без коректної прив'язки до профілю користувача або ресторану.

3.5 Розробка функцій роботи з БД
Для організації взаємодії між об'єктно-орієнтованим кодом серверної частини та реляційною базою даних Microsoft SQL Server використано технологію Entity Framework Core (EF Core). Це сучасний інструмент ORM, який дозволяє маніпулювати даними через об'єкти C#, автоматично транслюючи LINQ-запити в SQL-команди.
Взаємодія реалізована через клас контексту ApplicationDbContext, який зв’язується у контролери через механізм Dependency Injection. Нижче наведено реалізацію основних CRUD-операцій на прикладі розроблених контролерів.
Створення нових записів реалізовано через метод Add(), який переводить сутність у стан Added. Фіксація транзакції відбувається методом SaveChangesAsync(). Приклад з RestaurantsController.cs демонструє створення закладу з прив'язкою до власника (див. Б.1).
Читання реалізовано з використанням механізму Eager Loading (метод Include), що дозволяє одним запитом завантажити пов'язані дані (наприклад, замовлення разом зі стравами та користувачем). Також застосовано фільтрацію за допомогою Where. Приклад з OrdersController.cs (див. Б.2).
Оновлення відбувається через механізм Change Tracking. Спочатку сутність завантажується з БД, потім змінюються її властивості, і при виклику SaveChangesAsync EF Core генерує SQL-запит UPDATE тільки для змінених полів. Приклад зміни статусу замовлення в OrdersController.cs (PATCH-метод) (див. Б.3).
Видалення реалізовано через метод Remove(). Приклад з RestaurantsController.cs (див. Б.4)
Ці методи показують функціонал управління даними системи, включаючи обробку зв'язків (Foreign Keys) та виконання окремих бізнес-правил безпосередньо в транзакціях бази даних.
3.6 Розробка API для взаємодії серверної частини з клієнтами
Для організації взаємодії між серверною частиною та клієнтськими застосунками було обрано стиль REST, який базується на ресурсо-орієнтованому підході та ідеально відповідає структурі предметної області. Використання стандартних HTTP-методів (GET, POST, PATCH, DELETE) робить API передбачуваним, а легковаговий формат JSON гарантує швидкий та зручний обмін даними між різними платформами.
Система API розділена на логічні контролери, кожен з яких відповідає за певний домен. Нижче наведено реєстр основних маршрутів.
Контролер: AuthСontroller (Автентифікація та авторизація)
1. POST /api/Auth/register - реєстрація нового користувача в системі; перевіряє унікальність email, виконує хешування пароля (BCrypt) та створює запис у БД з роллю за замовчуванням (Customer).
2. POST /api/Auth/login - автентифікація користувача; перевіряє відповідність email та пароля, у разі успіху генерує та повертає JWT-токен доступу.
3. POST /api/Auth/forgot-password - ініціалізація процедури відновлення пароля; генерує унікальний токен скидання та зберігає його в БД з терміном дії 1 година (імітує відправку на email).
4. POST /api/Auth/reset-password - встановлення нового пароля; перевіряє валідність токена та змінює хеш пароля користувача.
5. GET /api/Auth/me - отримання профілю поточного користувача; потребує авторизації (Bearer Token).
Контролер: RestaurantsController (Заклади)
1. GET /api/Restaurants - отримання списку ресторанів; якщо передано необов'язкові параметри координат, список сортується за відстанню від користувача з використанням сервісу розрахунків.
2. GET /api/Restaurants/{id} - отримання детальної інформації про конкретний заклад, включаючи дані власника.
3. POST /api/Restaurants - створення нового ресторану; прив'язує заклад до вказаного власника (OwnerId) та встановлює статус активності.
4. DELETE /api/Restaurants/{id} - видалення закладу з бази даних.
Контролер: CategoriesController (Категорії їжі та напоїв)
1. GET /api/Categories - отримання списку категорій; приймає необов'язковий параметр restaurantId для фільтрації категорій конкретного ресторану.
2. POST /api/Categories - створення нової категорії меню для вказаного ресторану.
3. DELETE /api/Categories/{id} - видалення категорії.
Контролер: DishesController (Страви)
1. GET /api/Dishes - отримання списку страв; приймає необов'язковий параметр categoryId для фільтрації за категорією.
2. GET /api/Dishes/{id} - отримання детальної інформації про страву.
3. POST /api/Dishes - створення нової страви; приймає дані у форматі multipart/form-data для завантаження зображення, використовує сервіс IFileStorageService для збереження файлу та записує шлях до нього в БД.
4. DELETE /api/Dishes/{id} - видалення страви з меню.
Контролер: OrdersController (Замовлення)
1. GET /api/Orders - отримання історії замовлень; реалізує розмежування доступу: звичайний клієнт бачить лише власні замовлення, персонал може бачити всі.
2. GET /api/Orders/{id} - перегляд деталей конкретного замовлення; забороняє клієнту переглядати чужі замовлення (403 Forbidden).
3. POST /api/Orders - оформлення нового замовлення; валідує час візиту (не раніше ніж через 10 хвилин), розраховує загальну суму та використовує ICalculationService для визначення розрахункового часу готовності.
4. PATCH /api/Orders/{id}/status - зміна статусу замовлення (наприклад, на Ready); доступно лише для ролей Admin та KitchenStaff, при зміні статусу на Ready автоматично створює сповіщення для клієнта.
Контролер: NotificationsController (Сповіщення)
1. GET /api/Notifications - отримання списку сповіщень поточного користувача, відсортованих за часом (спочатку нові).
2. POST /api/Notifications/read/{id} - позначення конкретного сповіщення як "прочитаного".
Контролер: ReviewsController (Відгуки)
1. GET /api/Reviews/dish/{dishId} - отримання всіх відгуків до конкретної страви.
2. POST /api/Reviews - додавання нового відгуку (рейтинг + коментар) авторизованим користувачем.

3.8) Створення програмної реалізації API та функцій роботи з БД
Програмна реалізація серверної частини системи виконана на базі платформи .NET 8 із використанням фреймворку ASP.NET Core Web API. Обраний технологічний стек забезпечує високу продуктивність, кросплатформність та модульність розробки. Архітектура додатку дозволяє чітко розмежувати відповідальність між компонентами системи: шаром представлення (API Controllers), шаром бізнес-логіки (Services) та шаром доступу до даних (Data Access Layer).
Реалізація шару доступу до даних (Data Access Layer)
Взаємодія з базою даних Microsoft SQL Server реалізована за допомогою ORM Entity Framework Core. Центральним компонентом цього шару є клас ApplicationDbContext, який успадковує DbContext. У ньому визначено набори даних DbSet<T>, що представляють таблиці бази даних (Users, Restaurants, Orders тощо).
Для конфігурації підключення використано механізм Dependency Injection (DI). У файлі Program.cs зареєстровано контекст даних із використанням рядка підключення, винесеного у файл конфігурації appsettings.json. Entity Framework Core налаштовано на використання відстеження змін (Change Tracking), що дозволяє автоматично генерувати SQL-запити INSERT, UPDATE та DELETE при виклику методу SaveChangesAsync().
Реалізація логіки обробки запитів (API Controllers)
Приймання та обробка HTTP-запитів здійснюється контролерами API. Кожен контролер відповідає за окремий ресурс системи та реалізує повний набір CRUD-операцій. Використання асинхронної моделі програмування (async/await) дозволяє ефективно використовувати потоки веб-сервера, не блокуючи їх під час виконання тривалих операцій введення-виведення з базою даних.
Для передачі даних між клієнтом і сервером реалізовано патерн DTO (Data Transfer Object). Це дозволяє приховати внутрішню структуру сутностей бази даних, уникнути проблеми циклічних посилань при серіалізації в JSON та передавати клієнту лише необхідний набір полів. Мапінг (перетворення) між сутностями БД та DTO виконується вручну або за допомогою LINQ-виразів Select().
Інтеграція допоміжних сервісів
Частково бізнес-логіка винесена з контролерів у спеціалізовані сервіси, які також реєструються в DI-контейнері:
1. ICalculationService: Відповідає за математичні обчислення, зокрема розрахунок часу готовності замовлення на основі найтривалішого часу приготування страв у чеку, а також сортування ресторанів за географічною відстанню.
2. IFileStorageService: Забезпечує роботу з файловою системою для збереження зображень страв та логотипів ресторанів, повертаючи у БД лише відносний шлях до файлу.
3. IJwtTokenGenerator: Інкапсулює логіку створення та підписання токенів безпеки, забезпечуючи централізоване керування секретними ключами та часом життя сесії.


















4 ВИСНОВКИ
Під час виконання лабораторної роботи було проведено цикл проєктування та програмної реалізації серверної частини інформаційної системи попереднього замовлення страв та напоїв. Головною метою роботи було створення надійного, масштабованого та безпечного API, яке забезпечує взаємодію між клієнтськими застосунками, персоналом закладу та базою даних.
На етапі системного аналізу та моделювання було розроблено UML-діаграму прецедентів. Це дозволило чітко окреслити межі системи та ідентифікувати ключових акторів: Гостя, Клієнта, Власника ресторану та Персонал кухні (IoT-термінал). Було сформовано вимоги, де ключовою особливістю стала бізнес-логіка попереднього замовлення, яка, на відміну від класичних сервісів доставки, вимагає чіткої синхронізації часу приготування страв із часом візиту клієнта. Введення таких прецедентів, як «Вказати час самовивозу» та «Розрахунок часу готовності», дозволило закласти фундамент для коректної архітектури системи ще на етапі проєктування.
Важливим етапом роботи стало інформаційне моделювання предметної області. Було розроблено ER-діаграму, яка пройшла процес нормалізації до 3NF. Це дозволило усунути надмірність даних, позбутися транзитивних залежностей та забезпечити цілісність інформації. На основі логічної моделі було спроєктовано фізичну схему бази даних для СУБД Microsoft SQL Server. Особливу увагу було приділено типізації даних: для фінансових операцій використано тип DECIMAL для уникнення похибок округлення, для текстових полів встановлено обмеження NVARCHAR для оптимізації пам'яті, а часові мітки збережено у DATETIME. Реалізована схема бази даних, що включає таблиці Users, Restaurants, Orders, Dishes та інші, забезпечує надійне зберігання даних та ефективне виконання SQL-запитів.
Програмна реалізація серверної частини виконана на базі платформи .NET 8 із використанням технології ASP.NET Core Web API. Архітектура додатку побудована за принципами чистої архітектури з використанням патерну Dependency Injection (DI), що забезпечує слабку зв'язність компонентів та спрощує масштабування. Для взаємодії з базою даних використано ORM Entity Framework Core, що дозволило абстрагуватися від написання прямих SQL-запитів та працювати з даними як з об'єктами мови C#.
В ході роботи було розроблено RESTful API, яке охоплює всі необхідні бізнес-сценарії. Реалізовано п'ять основних контролерів:
1. AuthController: Забезпечує безпеку системи. Реалізовано реєстрацію та автентифікацію користувачів із використанням стандарту JWT (JSON Web Token). Паролі користувачів зберігаються виключно у хешованому вигляді (алгоритм BCrypt), що відповідає сучасним вимогам кібербезпеки.
2. RestaurantsController: Дозволяє керувати закладами та реалізує складну логіку сортування ресторанів за географічною відстанню до користувача, використовуючи математичні алгоритми обчислення координат.
3. CategoriesController та DishesController: Забезпечують управління контентом меню. Реалізовано підтримку завантаження медіа-файлів (зображень страв) через multipart/form-data із збереженням файлів на сервері та посилань у БД.
4. OrdersController: Реалізує центральний бізнес-процес системи. Забезпечено валідацію вхідних даних (перевірка часу візиту), автоматичний розрахунок вартості замовлення та прогнозування часу готовності. Реалізовано рольову модель доступу, де клієнт має доступ лише до власної історії, а персонал кухні може змінювати статуси замовлень.
5. NotificationsController та ReviewsController: Забезпечують комунікацію з користувачем та механізм зворотного зв'язку.
Для перевірки працездатності системи було проведено комплексне тестування розроблених ендпоінтів за допомогою інтерактивної документації Swagger UI. Тестування підтвердило коректність виконання CRUD-операцій, правильність роботи бізнес-логіки (зокрема, розрахунків та валідації) та надійність механізмів авторизації. Перевірка стану бази даних через SQL Server Management Studio підтвердила, що всі транзакції виконуються успішно, а посилальна цілісність даних зберігається.
Таким чином, в результаті виконання лабораторної роботи було створено бекенд для системи попереднього замовлення їжі. Отримані практичні навички роботи з .NET, Entity Framework Core, SQL Server та проєктування REST API дозволяють стверджувати, що розроблена архітектура є стійкою, безпечною та готовою до подальшого розвитку і впровадження клієнтської частини у наступних етапах роботи.

  1 [HttpGet]

  4 {

  7
  8     var query = _context.Orders
  9         .Include(o => o.Items).ThenInclude(i => i.Dish)
 10         .Include(o => o.User)
 11         .AsQueryable();
 12
 13     if (userRole == UserRole.Customer.ToString())
 14     {
 15         query = query.Where(o => o.UserId == userId);
 16     }
 17
 18     var orders = await query.OrderByDescending(o => o.CreatedAt).ToListAsync();
 19
 20     return Ok(orders.Select(MapToDto));
 21 }
