3 ОПИС ВИКОНАНОЇ РОБОТИ
Під час виконання лабораторної роботи було вирішено завдання реалізації бізнес-логіки серверної частини та функцій адміністрування програмної системи. Якщо на попередньому етапі основна увага приділялася проектуванню структури бази даних та контрактів API, то на цьому етапі розробка зосередилася на імплементації алгоритмів обробки даних, валідації бізнес-правил та забезпеченні інтерактивної взаємодії між компонентами системи. Розробка велася на базі платформи .NET 8 у межах шарів Application та Domain, що дозволило інкапсулювати складну логіку всередині сервісів та контролерів, залишивши шар даних відповідальним виключно за збереження інформації.
Реалізація бізнес-логіки охопила ключові процеси адміністрування та управління платформою: від автоматизації кадрового обліку та верифікації бізнес-акаунтів до генерації фінансової звітності та базового менеджменту локацій закладів. Особливий акцент було зроблено на інтеграції IoT, зокрема розроблено механізми інвентаризації пристроїв, моніторингу їх мережевого статусу та перевірки активності («пульсу») у реальному часі. Це дозволило забезпечити надійний контроль за станом підключеного обладнання та розмежування прав доступу до нього.
Паралельно було розроблено комплексний модуль адміністрування, необхідний для забезпечення безпеки та керованості системи. Він включає інструменти для управління життєвим циклом користувачів (блокування, зміна ролей), аналітичні дашборди, а також механізм аудиту, який фіксує критичні зміни даних та надає адміністраторам доступ до системних логів.
3.1) Реалізація бізнес-логіки серверної частини
Розробка бізнес-логіки була зосереджена в шарі сервісів (Services), що дозволило інкапсулювати складні обчислення та ізолювати їх від контролерів. Ключовим компонентом аналітичної підсистеми став клас StatisticsService (див. Додаток Б.3), який реалізує інтерфейс IStatisticsService. У ньому закладено алгоритми агрегації даних, фінансового аналізу та розрахунку навантаження закладу.
3.1.1)  Алгоритми фінансової аналітики та звітності
Для аналізу економічної ефективності закладу реалізовано метод GetDailyStatsAsync. Логіка методу базується на вибірці замовлень зі статусом Completed за вказаний часовий проміжок (from, to). Використання LINQ-оператора .GroupBy(o => o.CreatedAt.Date) дозволяє агрегувати дані по днях.

3.1.2) Алгоритм визначення пікових навантажень
Для оптимізації роботи персоналу реалізовано метод GetPeakLoadingAsync, який аналізує розподіл замовлень по годинах доби (0–23). Алгоритм працює за принципом відносної інтенсивності:

3.1.3) Товарна аналітика (найпопулярніші страви)
Метод GetTopDishesAsync відповідає за ранжування страв за популярністю. Він використовує об'єднання сутностей (.Include(oi => oi.Dish)), групування за назвою страви та сортування за спаданням кількості продажів (OrderByDescending). Це дозволяє виявити найбільш прибуткові позиції меню.
3.1.4) Workflow верифікації бізнесу
Процес затвердження нових закладів у системі реалізовано як суворий послідовний алгоритм («Подача заявки» → «Очікування» → «Валідація» → «Активація»), логіка якого інкапсульована у класі VerificationService (див. Додаток Б.4). Цей механізм виступає бар'єром проти шахрайства, гарантуючи, що доступ до функціоналу власника ресторану отримують лише перевірені контрагенти.
Перший етап - це ініціалізація процесу. Відбувається через метод подачі заявки (SubmitRequestAsync). На вхід метод приймає SubmitVerificationDto, що містить цифрову копію документів (у форматі IFormFile). На цьому етапі система виконує первинну технічну валідацію: перевіряється формат файлу (дозволено лише PDF або зображення. Після успішного завантаження документ зберігається у захищеному сховищі, а в базі даних створюється запис про заявку зі статусом Pending (Очікування). При цьому ресторан та обліковий запис власника залишаються неактивними/обмеженими.
Етап прийняття рішення покладено на адміністратора системи. Метод GetPendingRequestsAsync формує чергу заявок, які очікують розгляду, надаючи адміністратору доступ до завантажених документів. Процес валідації завершується викликом методу ProcessRequestAsync, який приймає DTO-модель із рішенням (IsApproved).
У разі позитивного рішення (Активація) система виконує транзакційну зміну станів: статус заявки змінюється на Approved, роль користувача автоматично підвищується до RestaurantOwner, а пов'язаний із ним ресторан переводиться у статус Active, стаючи видимим для клієнтів у загальному каталозі. У випадку відмови заявка маркується як Rejected, і права доступу користувача залишаються без змін.
3.1.5) Логіка кадрового менеджменту
Підсистема управління персоналом реалізована в класі StaffService і відповідає за регулювання трудових відносин між власниками закладів та користувачами платформи. Ключовою метою цього модуля є забезпечення цілісності штатного розпису та контроль за розподілом ролей у системі. Процес перетворення звичайного клієнта (Customer) на працівника кухні (KitchenStaff) відбувається через суворий алгоритм валідації, що унеможливлює конфлікти зайнятості.
Процедура найму (Hiring Workflow) ініціюється власником ресторану, який надсилає запит із даними кандидата (зазвичай через HireStaffDto). Перед затвердженням система виконує критичну перевірку на доступність («вільність») кандидата. Алгоритм звертається до профілю користувача і перевіряє поле RestaurantId: якщо воно не є порожнім (null), це означає, що користувач вже працевлаштований в іншому закладі. У такому випадку система блокує операцію, повертаючи помилку конфлікту. Якщо ж кандидат вільний, виконується транзакція: користувачу присвоюється ідентифікатор поточного ресторану, а його роль у системі змінюється на KitchenStaff, що надає доступ до інтерфейсу обробки замовлень.
Зворотний процес - звільнення (Termination). Реалізовано через метод, який розриває зв'язок між сутностями. При виклику цієї функції система перевіряє повноваження ініціатора (чи дійсно він є власником закладу, де працює співробітник). Після підтвердження виконується «м'яке» видалення зі штату: поле RestaurantId у профілі працівника очищується (встановлюється в null), а роль автоматично понижується до базового рівня Customer. Ця логіка гарантує, що звільнений працівник миттєво втрачає доступ до внутрішніх процесів кухні та IoT-пристроїв закладу.
3.1.5) Логіка IoT
Інтеграція фізичного обладнання (розумних печей, терміналів, кухонних екранів) реалізована через модуль IoTService, який виступає містком між програмною платформою та "залізом". 
Процес підключення нового обладнання проходить через метод RegisterDeviceAsync. Він реалізує сувору перевірку унікальності: система сканує базу за серійним номером (SerialNumber), і якщо такий пристрій вже існує, блокує спробу дублювання. При успішній реєстрації пристрій прив'язується до конкретного ресторану та фізичної локації (наприклад, "Гарячий цех" або "Бар"), отримуючи початковий статус Active.
Статус активності пристрою не зберігається в базі даних як статичне значення, а обчислюється динамічно в момент запиту. Система порівнює поточний час сервера з часовою міткою останнього отриманого сигналу (LastPing). Якщо інтервал часу, що минув з моменту останнього відгуку, не перевищує 5 хвилин, пристрій ідентифікуєтья як «Активний» (Online). У випадку, коли відсутність зв'язку триває довше встановленого порогового значення (понад 5 хвилин), система автоматично діагностує втрату з'єднання та маркує пристрій статусом «Недоступний» (Offline).
Управління парком пристроїв (додавання, видалення) суворо захищене у контролері IoTDevicesController. Використовується кастомний метод валідації CheckAccess, який гарантує ізоляцію даних: власник Ресторану А не може випадково або навмисно видалити обладнання, що належить Ресторану Б. Спроба доступу до чужого пристрою автоматично повертає статус 403 Forbidden.
3.2) Функції адміністрування та безпеки
Розробка адміністративної панелі була спрямована на створення централізованого центру управління системою, який забезпечує контроль над користувачами, бізнес-суб'єктами та фінансовими потоками. Реалізація базується на контролері AdminController (див. Додаток Б.1), доступ до якого суворо регламентований атрибутом авторизації [Authorize(Roles = "Admin")]. Це гарантує, що жоден запит до методів управління не буде виконаний без валідного JWT-токена з відповідними правами доступу.
3.2.1) Управління життєвим циклом користувачів (Access Control)
Підсистема контролю доступу (Access Control) забезпечує гнучке управління правами учасників платформи. Реалізовано механізм примусової зміни статусів облікових записів, що є критично важливим для забезпечення безпеки системи. Операція блокування порушників виконується через метод BlockUser, який приймає об'єкт передачі даних BlockUserDto. Логіка методу передбачає не видалення запису з бази даних, а зміну його стану («soft delete» або IsBanned = true), що дозволяє зберегти історію дій користувача.
Паралельно функціонує система управління ролями (Role-Based Access Control). Через метод ChangeRole адміністратор має можливість динамічно змінювати рівень привилеїв користувача (наприклад, підвищення клієнта до статусу «Менеджер» або «Власник ресторану»). Використання DTO (ChangeRoleDto) дозволяє чітко типізувати цей процес, унеможливлюючи помилкові призначення неіснуючих ролей.
3.2.2) Управління суб'єктами бізнесу
Для контролю за діяльністю партнерів (ресторанів) реалізовано інструментарій прямого впливу на їхню доступність у системі. Метод ToggleRestaurantStatus дозволяє адміністратору втручатися в роботу закладу в екстрених випадках (наприклад, при виявленні порушень санітарних норм або несплаті комісії). Зміна статусу відбувається миттєво: встановлення прапорця isActive = false на рівні бази даних автоматично виключає ресторан із видачі клієнтського API, роблячи його невидимим для замовників. Цей механізм реалізовано на рівні сервісного шару, що забезпечує узгодженість даних у всіх модулях системи.
3.2.3) Система аудиту та моніторингу
З метою забезпечення прозорості управлінських рішень та можливості ретроспективного аналізу інцидентів впроваджено систему логування активності. Метод GetRecentLogs надає адміністратору доступ до журналу подій, де фіксуються критичні дії в системі. Кожен запис аудиту містить інформацію про ініціатора дії (ID адміністратора), тип операції (наприклад, «Блокування користувача»), часову мітку та об'єкт впливу. Це дозволяє побудувати повний ланцюжок подій ("audit trail") у випадку розслідування конфліктних ситуацій або підозрілої активності.
3.2.4) Функціонал системної аналітики
Для забезпечення адміністратора актуальною інформацією про стан платформи реалізовано механізм централізованої агрегації даних. Замість виконання десятків окремих запитів до бази даних, розроблено спеціалізований метод GetSystemDashboardAsync (у сервісі StatisticsService), який формує комплексний аналітичний зріз системи в реальному часі.
Цей функціонал повертає структурований об'єкт даних (AdminDashboardDto), що містить ключові метрики ефективності (KPI). Одним із головних розрахункових показників є частка ринку (Revenue Share), яка визначає фінансову вагу конкретного ресторану в загальному обігу платформи.
 Математична модель розрахунку виглядає наступним чином:
  
, де
Si - частка ринку i-го ресторану (у відсотках);
Ri - сумарна виручка конкретного ресторану (сума всіх замовлень зі статусом Completed);
Rtotal - загальний грошовий обіг (Total System Revenue) всієї платформи, що розраховується як сума виручки всіх активних закладів
  
, де
Rtotal - загальний фінансовий обіг (Total System Revenue) всієї платформи;
М - загальна кількість активних ресторанів, зареєстрованих у системі;
Rk - сумарна виручка окремого k-го ресторану (сума всіх його завершених замовлень);
k - індекс ітерації, що проходить від 1 (першого) до M (останнього) закладу в списку.
3.3) UML-діаграми діяльності програми
3.3.1) Моделювання процесу обробки замовлення 
Представлена діаграма діяльності відображає шлях замовлення в системі: від натискання кнопки «Замовити» клієнтом до повної готовності страв. Основна увага тут приділяється тому, як серверна частина контролює цей процес, поєднуючи автоматичні перевірки з реальними діями персоналу кухні. Взаємодія відбувається між трьома учасниками: клієнтським застосунком, сервером (API) та інтерфейсом кухаря.
Процес починається з етапу валідації, який виступає своєрідним «фільтром» на вході в систему. Коли сервер отримує запит на створення замовлення, він першочергово перевіряє вказаний час візиту (VisitTime). Якщо клієнт хоче отримати замовлення швидше, ніж за 10 хвилин, система автоматично блокує таку спробу, повертаючи помилку. Це необхідний запобіжник, який гарантує, що кухня матиме фізично достатньо часу для приготування їжі, і замовлення не «зависне» як прострочене ще до початку роботи.
Якщо перевірка часу пройшла успішно, вмикається основна бізнес-логіка: сервер завантажує актуальні ціни з бази даних, підсумовує вартість та фіксує замовлення зі статусом «Очікування» (Pending). Після цього ініціатива переходить до персоналу кухні. Діаграма демонструє, що сервер не просто зберігає дані, а реагує на дії кухарів: як тільки статус змінюється на «Готується» або «Готово», система миттєво оновлює інформацію в базі даних та надсилає клієнту сповіщення, тримаючи його в курсі прогресу виконання.

3.3.2) Алгоритм найму працівника
Наступна діаграма діяльності деталізує логіку кадрового модуля, а саме - процедуру додавання нового співробітника до штату ресторану. Цей процес є критичним з точки зору безпеки, оскільки він надає користувачеві доступ до внутрішньої "кухні" закладу. Тому алгоритм побудовано за принципом каскадної валідації: перш ніж внести зміни, сервер виконує три рівні перевірок.
Процес ініціюється власником закладу, який надсилає серверу Email кандидата. Перший етап - це перевірка існування: система шукає користувача в базі даних, і якщо такої пошти не зареєстровано, процес миттєво переривається помилкою 404 Not Found. Другий етап - перевірка ролі: система забороняє наймати привілейованих користувачів (інших власників або адміністраторів), щоб уникнути конфліктів ієрархії.
Третій, фінальний етап валідації - це перевірка зайнятості. Сервер аналізує поле RestaurantId кандидата, щоб переконатися, що він не працює в іншому закладі. Це запобігає ситуаціям, коли один працівник має доступ до даних конкурентів. Лише після успішного проходження всіх фільтрів система виконує фінальну дію: змінює роль користувача на KitchenStaff та прив'язує його до поточного ресторану, завершуючи процедуру успішним статусом 200 OK.


  

Рисунок 3.2 - UML-діаграми діяльності “Алгоритм найму працівника”
3.3.3) Процес верифікації та активації власника бізнесу 
Завершальна діаграма діяльності демонструє адміністративний процес легалізації нового партнера в системі. Цей алгоритм є прикладом підходу «Human-in-the-loop», де критичні рішення щодо надання доступу до бізнес-функціоналу приймає людина (адміністратор), а система забезпечує виконання цього рішення та його протоколювання.
Процес розпочинається з ручної перевірки: адміністратор аналізує чергу заявок та переглядає прикріплені юридичні документи. На цьому етапі відбувається розгалуження процесу. У випадку виявлення невідповідностей (гілка «Ні») серверна логіка обмежується зміною статусу заявки на Rejected та відправкою пояснення користувачеві, без зміни його прав у системі.
Гілка успішної верифікації («Так») ініціює складнішу транзакцію на стороні сервера. При схваленні заявки контролер не просто змінює її статус, а й модифікує сутність користувача, підвищуючи його роль до RestaurantOwner. Ця дія є незворотною в межах даного процесу і відкриває користувачеві доступ до панелі управління рестораном. Важливою деталлю, відображеною на діаграмі, є обов'язковий запис у журнал аудиту (Audit Log): система фіксує, хто саме з адміністраторів і коли прийняв рішення, забезпечуючи повну прозорість та підзвітність дій персоналу.
  

Рисунок 3.3 - UML-діаграми діяльності “Процес верифікації та активації власника бізнесу”
3.4) UML-діаграми взаємодії програми
Наведена діаграма візуалізує найважливіший бізнес-процес платформи - оформлення клієнтом попереднього замовлення. Вона демонструє часову послідовність викликів між API-контролером, допоміжними сервісами та шаром збереження даних.
Процес ініціюється HTTP-запитом POST до OrdersController (див. Додаток Б.2). Першим критичним кроком є внутрішня валідація даних: контролер перевіряє бізнес-правило щодо часу візиту (замовлення не може бути "на зараз", мінімальний інтервал - 10 хвилин). Це запобігає створенню замовлень, які кухня фізично не встигне виконати.
Далі діаграма ілюструє принцип «Server-Side Authority»: ціни на страви беруться не із запиту клієнта, а витягуються безпосередньо з бази даних (Database), що гарантує фінансову безпеку та захист від маніпуляцій. Для розрахунку прогнозованого часу готовності контролер звертається до окремого компонента CalculationService, дотримуючись принципу єдиної відповідальності (SRP). Життєвий цикл завершується збереженням сформованої сутності замовлення зі статусом Pending та поверненням клієнту відповіді 201 Created з деталями створеного об'єкта.

130         [HttpPatch("{id}/status")]
131         [Authorize(Roles = "Admin,KitchenStaff")]
132         public async Task<IActionResult> UpdateOrderStatus(int id, [FromBody] UpdateOrderStatusDto dto)
133         {
134             var order = await _context.Orders
135                 .Include(o => o.Restaurant)
136                 .FirstOrDefaultAsync(o => o.Id == id);
137
138             if (order == null) return NotFound();
139
140             var userId = int.Parse(User.FindFirstValue(ClaimTypes.NameIdentifier)!);
141             var userRole = User.FindFirstValue(ClaimTypes.Role);
142
143             if (userRole != UserRole.Admin.ToString())
144             {
145                 if (userRole == UserRole.Admin.ToString() && order.Restaurant.OwnerId != userId)
146                     return StatusCode(403, "Ви не можете керувати замовленнями чужого ресторану!");
147
148                 if (userRole == UserRole.KitchenStaff.ToString())
149                 {
150                     var staffUser = await _context.Users.FindAsync(userId);
151                     if (staffUser == null || staffUser.RestaurantId != order.RestaurantId)
152                         return StatusCode(403, "Ви не є працівником цього ресторану!");
153                 }
154             }
155
156             var oldStatus = order.Status;
157             order.Status = dto.Status;
158
159             string? notificationMessage = null;
160
161             switch (dto.Status)
162             {
163                 case OrderStatus.Pending:
164
165                     break;
166
167                 case OrderStatus.Paid:
168                     notificationMessage = $"Оплату за замовлення #{order.Id} отримано. Дякуємо!";
169                     break;
170
171                 case OrderStatus.Cooking:
172
173                     if (oldStatus == OrderStatus.Pending || oldStatus == OrderStatus.Paid)
174                     {
175                         notificationMessage = $"Кухня почала готувати ваше замовлення #{order.Id}. Скоро буде смачно!";
176                     }
177                     break;
178
179                 case OrderStatus.Ready:
180                     notificationMessage = $"Ваше замовлення #{order.Id} готове до видачі! Чекаємо на вас.";
181                     break;
182
183                 case OrderStatus.Completed:
184                     notificationMessage = $"Дякуємо, що обрали {order.Restaurant.NameUA}! Будемо вдячні за ваш відгук у додатку.";
185
186                     break;
187
188                 case OrderStatus.Cancelled:
189                     notificationMessage = $"Ваше замовлення #{order.Id} було скасовано. Якщо це помилка, зверніться до персоналу.";
190
191                     break;
192             }
193
194             if (!string.IsNullOrEmpty(notificationMessage))
195             {
196                 var notification = new Notification
197                 {
198                     UserId = order.UserId,
199                     Message = notificationMessage,
200                     DateSent = DateTime.UtcNow,
201                     IsRead = false
202                 };
203                 _context.Notifications.Add(notification);
204             }
205
206             await _context.SaveChangesAsync();
207             return Ok(new { message = $"Статус змінено на {order.Status}", notificationSent = notificationMessage != null });
208         }

 68                 else if (count >= maxOrders * 0.4) intensity = "⚠️ Medium";
 69                 else intensity = "🟢 Low";
 70
 71                 result.Add(new PeakLoadDto
 72                 {
 73                     Hour = i,
 74                     OrdersCount = count,
 75                     Intensity = count > 0 ? intensity : "🟢 Low"
