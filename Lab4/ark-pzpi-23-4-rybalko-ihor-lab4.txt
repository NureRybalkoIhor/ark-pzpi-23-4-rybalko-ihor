	2 ЗАВДАННЯ
1. Розробити будову програмного забезпечення IoT клієнта:
   1. Спроектувати архітектуру IoT клієнта, враховуючи його призначення та взаємодію з серверною частиною. Розробити загальну структуру, включаючи модулі обробки даних, мережевих протоколів та управління пристроями.
2. Створити UML діаграму прецедентів для IoT клієнта:
   1. Діаграма прецедентів повинна описувати основні сценарії взаємодії користувача та системи з IoT клієнтом. Це можуть бути такі прецеденти, як «Налаштування параметрів клієнта», «Надсилання даних на сервер», «Оновлення прошивки» тощо.
3. Розробити бізнес логіку та функції налаштування IoT клієнта:
   1. Розробити основну бізнес логіку для роботи з даними пристроїв (зчитування, відправлення на сервер тощо).
   2. Розробити функції налаштування IoT клієнта (конфігурування мережі, параметрів підключення, управління енергоспоживанням).
4. Створити UML діаграму діяльності для IoT клієнта:
   1. Діаграма діяльності повинна відображати основні дії IoT клієнта, наприклад, послідовність дій при передачі даних на сервер, процес з'єднання з мережею або оновлення прошивки.
5. Створити програмну реалізацію бізнес логіки та функцій налаштування IoT клієнта:
   1. Реалізувати програмний код для виконання бізнес логіки, включаючи обробку даних з датчиків, комунікацію із серверною частиною через мережеві протоколи (наприклад, MQTT, HTTP).
   2. Реалізувати налаштування IoT клієнта, такі як конфігурація мережі, перезавантаження або відновлення параметрів за замовчуванням.
6. Перевірити роботу IoT клієнта:
   1. Провести тестування розроблених компонентів IoT клієнта, перевіривши коректність обміну даними із сервером, функціональність налаштувань та стабільність роботи.


















3 ОПИС ВИКОНАНОЇ РОБОТИ
4.1) Розроблення будови програмного забезпечення ІоТ клієнта
Програмне забезпечення IoT-клієнта базується на принципах модульності, що дозволяє ізолювати низькорівневу роботу з «залізом» від високорівневої бізнес-логіки та мережевого стеку. Використання концепції Edge Computing на базі ESP32 дозволяє перенести частину обчислювального навантаження з хмари безпосередньо на периферію. Це критично важливо для систем реального часу, таких як KDS (Kitchen Display System), де затримки в обробці статусів можуть призвести до порушення технологічного процесу приготування страв. Кожен модуль спроектований так, щоб бути максимально незалежним, що спрощує подальше масштабування системи, наприклад, при додаванні нових сенсорів або зміні типу дисплея.
Модуль бізнес-логіки реалізує архітектуру скінченного автомата (Finite State Machine), яка гарантує цілісність даних. Математична обробка в цьому модулі базується на точному вимірюванні інтервалів між подіями за допомогою системного таймера millis(). На відміну від серверного часу, який може залежати від затримок мережі, локальне вимірювання на ESP32 дає похибку менше мілісекунди. Пристрій оперує динамічними змінними для збереження станів замовлення, де зміна статусу з Cooking (2) на Ready (3) автоматично ініціює розрахунок дельти часу приготування. Цей показник аналізується на пристрої перед відправкою, що дозволяє виявляти аномалії (наприклад, занадто швидке закриття замовлення) ще до того, як дані потраплять у базу даних.
Мережева взаємодія реалізована через оптимізований стек протоколів, де вибір методу HTTP PATCH замість стандартного PUT чи POST обумовлений необхідністю мінімізації трафіку. Оскільки ми оновлюємо лише статус замовлення, такий підхід дозволяє передавати JSON-пакети мінімального розміру, що прискорює проходження даних через тунелі ngrok. Використання бібліотеки ArduinoJson для серіалізації забезпечує строгу типізацію даних, що відповідає серверним моделям C# (DTO). Важливим аспектом є обробка виняткових ситуацій у мережі: клієнт має логіку перевірки статус-кодів відповіді (наприклад, 200 OK), що відображається на фізичному рівні, запобігаючи втраті даних у разі обриву тунелю.
Управління периферійними пристроями реалізовано через рівень абстракції, який фільтрує фізичні шуми. Наприклад, обробка вхідного сигналу від кнопки включає алгоритм програмного антибрязкоту (debounce): мікроконтролер ігнорує будь-які зміни стану піна протягом 50 мілісекунд після першого спрацювання, що запобігає множинним відправкам запитів на сервер при одному натисканні. Візуалізація через шину I2C на дисплеї LCD1602 дозволяє звільнити GPIO-піни ESP32 для інших завдань, а звукова індикація через бузер використовує широтно-імпульсну модуляцію (PWM) для створення різних тональностей, що допомагає персоналу кухні розрізняти успішну синхронізацію та помилку з'єднання без необхідності постійно дивитися на екран.
4.2) Створення UML діаграми прецедентів для IoT клієнта
Представлена UML діаграма прецедентів (рисунок 4.1) описує модель розподіленої IoT-системи, що базується на принципах поділу відповідальності між клієнтською периферією та хмарним бекендом. В основі цієї моделі лежить концепція синхронізації фізичних дій персоналу з віртуальним станом об'єктів у базі даних. Центральним елементом системи є IoT-клієнт, який виступає посередником між акторами «Customer» (Клієнт) та «Kitchen Staff» (Кухар), забезпечуючи повний життєвий цикл замовлення від ініціації до фіналізації.
Процес взаємодії розпочинається з боку зовнішнього користувача через прецеденти створення замовлення та проведення оплати. Рішення підходу полягає в автоматичній фільтрації потоку даних: серверна частина оновлює стан замовлення в базі даних до значення «Paid» (статус 1), і лише після цього замовлення стає валідним для відображення на IoT-терміналі. Це реалізує механізм захисту ресурсів системи від обробки фінансово непідтверджених запитів, що критично важливо для стабільності роботи черги на виробничій ділянці.
Основна операційна логіка зосереджена в прецеденті оновлення статусу, який ініціюється кухарем через фізичний інтерфейс пристрою. Цей прецедент інтегрує в себе складну математичну обробку, спрямовану на обчислення часових метрик приготування страв (Efficiency KPI). Завдяки використанню технології Edge Computing, IoT-клієнт самостійно фіксує інтервали між зміною статусів, що дозволяє отримувати точні аналітичні дані про продуктивність кухні без потреби в постійних високочастотних запитах до центрального процесора сервера.
Мережева взаємодія в межах даної UML діаграми реалізується через спеціалізований прецедент синхронізації даних із використанням тунелювання ngrok. Ця технологія дозволяє IoT-пристрою, що знаходиться в ізольованій мережі симулятора, здійснювати безпечні HTTP PATCH запити до локального .NET сервера. Завершальним етапом є автоматична генерація сповіщень, яка тригериться сервером після успішної транзакції даних у базу SQL Server. Таким чином, діаграма демонструє замкнутий інформаційний контур, де фізична дія на периферійному пристрої стає джерелом для оновлення великих даних та миттєвого інформування споживача.

4.3) Розроблення бізнес логіки та функцій налаштування ІоТ клієнта
Програмне забезпечення IoT-клієнта, зосереджене у файлі main.cpp, працює за принципом інтелектуального фільтра, який не просто передає натискання кнопки, а самостійно керує станами замовлення. В основі лежить модель скінченного автомата, яка слідкує за тим, щоб статуси змінювалися лише у логічній послідовності, наприклад, від «Оплачено» до «Готується». Математична складова тут проявляється у розрахунку коефіцієнта продуктивності. Використовуючи функцію millis(), пристрій фіксує точний час початку та завершення роботи над стравою. На основі цих даних обчислюється тривалість приготування за формулою ∆T = (Tend - Tstart) / 1000. Ці розрахунки дозволяють відправляти на сервер не просто «сухий» статус, а готову аналітику, що допомагає оцінити швидкість роботи кухні без додаткових обчислень на боці бази даних.
Для того, щоб система працювала швидше, ми впроваджуємо логіку оптимістичного оновлення інтерфейсу. Як тільки кухар натискає кнопку, LCD-дисплей та звуковий сигнал миттєво реагують, даючи підтвердження, а мережевий запит на сервер відправляється у фоновому режимі. Це дозволяє персоналу не чекати кілька секунд, поки дані пройдуть через тунель ngrok до сервера. З точки зору математики, ми також закладаємо алгоритм Exponential Backoff для обробки помилок: якщо інтернет зник, пристрій не намагається слати запити щосекунди, а поступово збільшує паузу між спробами. Це запобігає «зависанню» мікроконтролера та зайвому навантаженню на мережевий модуль, дозволяючи системі самостійно відновитися після збою.
Функції налаштування в нашому проекті розроблені таким чином, щоб пристрій міг легко адаптуватися до змін у мережі без перепрошивки коду. Замість того, щоб жорстко прописувати адресу сервера, ми закладаємо можливість динамічного оновлення URL. Оскільки посилання у безкоштовному ngrok змінюється після кожного перезапуску, пристрій може бути налаштований на автоматичне отримання актуальної адреси бекенду. Також налаштування включають ідентифікацію через унікальний серійний номер (serialNum), який додається до кожного HTTP-запиту. Це дозволяє серверу миттєво впізнати конкретний термінал і прив'язати його до потрібного цеху або ресторану в базі даних SQL Server, забезпечуючи високий рівень безпеки без використання складних паролів на кожному кроці.
Важливою частиною конфігурації є керування ресурсами та енергоспоживанням, що особливо важливо для стабільної роботи ESP32. Програма містить функції налаштування яскравості дисплея та частоти опитування мережі залежно від інтенсивності роботи. Якщо замовлень немає довгий час, пристрій переходить у режим зниженої активності, а під час «години пік» - автоматично прискорює обробку подій. Крім того, ми додаємо можливість «гарячого» налаштування через сервісне меню, яке активується довгим натисканням кнопки. Це дозволяє прямо на екрані LCD побачити поточну IP-адресу, силу сигналу Wi-Fi та статус підключення до сервера, що значно полегшує діагностику системи під час реальної експлуатації або захисту лабораторної роботи.
4.4) Створення UML діаграми діяльності для IoT клієнта (дивитись рисунок Б.1)
Діаграма діяльності починається з фази ініціалізації, де система готує апаратні ресурси до роботи. На цьому етапі відбувається конфігурація послідовного порту для логування, налаштування шини I2C для виводу даних на дисплей та визначення режиму роботи GPIO-пінів для обробки сигналів від фізичної кнопки. Після завершення базових налаштувань програма переходить до критичного вузла - встановлення зв’язку з бездротовою мережею. Цей процес реалізований як циклічна операція (repeat-while), яка триває до моменту отримання успішного статусу з’єднання. Тільки після підтвердження доступу до мережі на LCD-дисплей виводиться статус готовності системи, що сигналізує про перехід термінала в режим очікування замовлень.
Основний операційний цикл системи побудований на подієво-орієнтованому підході. При виявленні сигналу від кнопки програма активує блок фільтрації брязкоту контактів, що гарантує цілісність логічного сигналу. Центральною частиною цього етапу є бізнес-логіка інкрементації статусів замовлення від 0 до 4. Саме тут реалізована математична модель оцінки ефективності: система аналізує поточний стан і, якщо замовлення переходить у статус «Cooking» або «Completed», фіксує відповідні часові мітки в мілісекундах. Розрахунок дельти часу (∆T) безпосередньо на мікроконтролері дозволяє отримати точний показник тривалості виробничого процесу, який надалі використовується для аналітики продуктивності кухні.
Завершальна частина діаграми діяльності описує процес синхронізації локальних даних із хмарною базою даних через тунель ngrok. Після математичної підготовки даних пристрій формує JSON-пакет, який містить оновлений статус замовлення. Процес передачі включає встановлення HTTP-з’єднання з використанням методу PATCH та додавання спеціалізованих заголовків для коректної маршрутизації трафіку. Логіка діаграми передбачає обов’язкову перевірку коду відповіді сервера: у разі успішного оновлення (HTTP 200) система видає звуковий сигнал та оновлює інформацію на дисплеї. Якщо виникає помилка з’єднання, алгоритм активує механізм повторних спроб із поступовим збільшенням затримки, що забезпечує стабільність системи в умовах нестабільного інтернет-зв’язку.
4.5 ) Програмна реалізація (дивитись Додаток В.1) бізнес-логіки та функцій налаштування IoT
Програмне забезпечення IoT-клієнта починає свою роботу з активації мережевого стеку, який налаштований на роботу в публічних мережах. Замість статичних локальних IP-адрес, система використовує динамічне підключення до Wi-Fi та ініціалізацію HTTP-клієнта, орієнтованого на роботу з сервісами тунелювання. Це дозволяє пристрою звертатися до ендпоїнта сервера за адресою https://[ngrok-url]/api/Orders/iot, де серійний номер пристрою виступає в ролі динамічного параметра аутентифікації. Такий підхід забезпечує безпеку з’єднання, оскільки сервер ідентифікує термінал не за IP-адресою, а за його унікальним цифровим відбитком у базі даних.
Математичний блок ПЗ відповідає за перетворення фізичних інтервалів часу у бізнес-метрики продуктивності. При переході замовлення у стан «Cooking» (2), клієнт ініціює запис часової мітки за допомогою функції millis(). При фіналізації замовлення у стан «Completed» (4), обчислюється тривалість приготування страви за алгоритмом ∆ T = (Tend - Tstart) / 1000. Цей показник не просто виводиться на LCD-дисплей, а інтегрується у JSON-об'єкт як додаткове поле аналітики. Така обробка на боці клієнта дозволяє розвантажити сервер і надати йому вже готові статистичні дані для подальшого аналізу ефективності роботи персоналу.
Бізнес-логіка відправлення даних базується на використанні методу HTTP PATCH, що є оптимальним для часткового оновлення стану замовлення в SQL Server. Для коректної передачі інформації використовується бібліотека ArduinoJson, яка формує пакет даних із полями Status та UpdateAt. Важливим технічним рішенням є впровадження спеціалізованого заголовка ngrok-skip-browser-warning: true. Це дозволяє ПЗ ігнорувати проміжну HTML-сторінку ngrok і відправляти JSON-потік безпосередньо до .NET-контролера. Програма також реалізує логіку обробки статус-кодів сервера: успішне оновлення (200 OK) ініціює звукову індикацію, а помилка (наприклад, 404 - замовлення не знайдено) призводить до візуалізації коду помилки для оператора.
Для забезпечення роботи IoT-клієнта на серверній частині реалізовано специфічну архітектуру даних. Основним ендпоїнтом для взаємодії є PATCH /api/Orders/iot/{id}/status, який приймає ідентифікатор замовлення та оновлені параметри. Для розширення функціоналу було додано нову таблицю в базу даних - IoTDevices, яка зберігає зв'язки між серійними номерами пристроїв та конкретними кухнями. Це дозволяє реалізувати предиктивну бізнес-логіку: якщо пристрій з певним serialNumber намагається оновити замовлення, яке до нього не відноситься, сервер заблокує таку дію, гарантуючи цілісність та безпеку всієї системи автоматизації.

  4 {
  5     var device = await _context.IoTDevices.FirstOrDefaultAsync(d => d.SerialNumber == serialNumber && d.IsActive);
  6     if (device == null) return Unauthorized("Пристрій не зареєстровано або він заблокований");
  7
  8     var order = await _context.Orders
  9         .Include(o => o.Restaurant)

 11
 12     if (order == null) return NotFound("Замовлення не знайдено");
 13
 14     if (order.RestaurantId != device.RestaurantId)
 15         return StatusCode(403, "Цей термінал не має прав на керування цим замовленням");
 16
 17     var oldStatus = order.Status;
 18     order.Status = dto.Status;
 19
 20     string? notificationMessage = null;
 21

 26             break;

 29             if (oldStatus == OrderStatus.Pending || oldStatus == OrderStatus.Paid)

 31                 notificationMessage = $"Кухня почала готувати замовлення #{order.Id}. Скоро буде смачно!";
