3 ОПИС ВИКОНАНОЇ РОБОТИ
Процес розгортання розпочався з глибокої підготовки вихідного коду для роботи в ізольованому середовищі. Головною метою було перетворити локальний додаток .NET та супутні модулі на стандартизовані Docker-образи. Це дозволяє уникнути класичної проблеми «на моєму комп'ютері працює», оскільки контейнер містить у собі абсолютно всі необхідні бібліотеки, змінні оточення та системні залежності, які потрібні для стабільного функціонування програмного комплексу.
Для основного бекенд-сервісу FoodPreOrder було застосовано технологію багатоетапної збірки (Multi-stage build). Це стратегічне рішення дозволило розділити процес на два незалежні кроки всередині одного Dockerfile (дивитися Додаток Б.1). На першому етапі (Build) використовувався повноважний образ SDK 8.0, у якому відбувалося відновлення залежностей через NuGet та компіляція проекту. На другому етапі (Runtime) готові бінарні файли переносилися в значно легший та безпечніший образ ASP.NET Core Runtime. Це дозволило отримати компактний фінальний образ, який не містить зайвих інструментів розробки та вихідного коду.
Окрему увагу було приділено модулю IoT. Його контейнеризація дозволила імітувати роботу автономного пристрою в межах єдиної інфраструктури. Завдяки власному Dockerfile (дивитися Додаток Б.3), IoT-клієнт отримав власне ізольоване середовище виконання, що дозволяє йому працювати паралельно з API. Це демонструє гнучкість системи, де кожен компонент (мікросервіс) може масштабуватися та оновлюватися незалежно від інших, зберігаючи при цьому стабільний зв'язок через віртуальну мережу Docker.
Наступним кроком стала розробка файлу оркестрації docker-compose.yml (дивитися Додаток Б.2 та Б.4 відповідно), який став «інструкцією» для всієї системи. У ньому було задекларовано три ключові сервіси: базу даних MS SQL Server, API-сервіс та IoT-модуль. Використання Compose дозволило не лише запускати всі компоненти однією командою, а й налаштувати автоматичне керування ресурсами. Зокрема, було визначено мапінг портів, де внутрішній порт контейнера (наприклад, 8080) було перенаправлено на зовнішній порт 5000 хост-машини, що забезпечило доступ до Swagger-інтерфейсу через звичайний веб-браузер.
Важливим елементом підготовки стала оптимізація контексту збірки за допомогою файлу .dockerignore. У нього було внесено папки компіляції (bin, obj), приховані налаштування середовища (.vs, .vscode) та історію контролю версій. Це дозволило значно прискорити процес створення образів, оскільки Docker перестав копіювати сотні мегабайтів непотрібних тимчасових файлів всередину контейнера. У результаті збірка образу стала відбуватися швидше, а сам образ став більш професійним та очищеним від сміття розробки.
Центральним завданням цього етапу стало налагодження стабільного зв'язку між контейнером API та контейнером бази даних MS SQL Server. На відміну від локальної розробки, де звернення відбувається до localhost, у середовищі Docker кожен контейнер має власну IP-адресу. Для вирішення цієї проблеми було використано механізм Docker DNS, який дозволяє сервісам звертатися один до одного за іменами, вказаними в docker-compose.yml. Таким чином, у рядку підключення (Connection String) замість конкретної адреси було вказано ім'я сервісу db, що зробило конфігурацію гнучкою та незалежною від внутрішньої мережевої структури Docker.
Окрему увагу було приділено безпеці та управлінню конфігураціями. Усі критичні параметри, такі як пароль адміністратора бази даних (SA_PASSWORD) та порти підключення, були винесені у змінні оточення (Environment Variables). Це дозволило відокремити програмний код від налаштувань інфраструктури, що є однією з ключових вимог методології розробки хмарних застосунків. Завдяки цьому систему можна легко розгорнути на будь-якому іншому сервері, просто змінивши значення в одному файлі конфігурації, не втручаючись у вихідний код проекту.
Одним із найважливіших досягнень на цьому етапі стала повна автоматизація розгортання схеми даних. Оскільки база даних у Docker-контейнері спочатку є абсолютно порожньою, було реалізовано механізм автоматичного застосування міграцій при старті додатка. У файл Program.cs було інтегровано блок коду, який за допомогою Entity Framework Core перевіряє стан бази даних та автоматично створює всі необхідні 16 таблиць (Users, Dishes, Orders тощо) та зв’язки між ними. Це гарантує, що система буде готова до роботи відразу після запуску контейнерів, незалежно від наявності попередньо налаштованої бази.
Для забезпечення відтворення системи було налаштовано постійне зберігання даних (Volumes). Хоча контейнери за своєю природою є тимчасовими (ephemeral), використання Docker Volumes дозволяє зберігати файли бази даних на фізичному диску хост-машини. Це означає, що навіть при перезапуску або видаленні контейнера з SQL Server, усі замовлення, дані користувачів та налаштування ресторанів залишаться цілими. Такий підхід забезпечує надійність промислового рівня для розгорнутої програмної системи.
Після успішного розгортання інфраструктури було проведено комплексне тестування функціональних можливостей системи. Основним інструментом для перевірки став інтерфейс Swagger UI, доступ до якого було забезпечено через прокидання портів на http://localhost:5000/swagger. Це дозволило протестувати всі API-ендпоінти в реальному часі, взаємодіючи безпосередньо з базою даних, що працює в Docker-контейнері. Зокрема, було успішно проведено операції реєстрації нових користувачів та авторизації, що підтвердило коректність роботи логіки безпеки та JWT-автентифікації в ізольованому середовищі.
Для забезпечення стабільної валідації даних на рівні моделей (DTO) було прийнято рішення використовувати англомовні повідомлення про помилки. Це гарантує, що при отриманні некоректних вхідних даних (наприклад, невірного формату телефону або занадто короткого пароля), система повертає чітку та зрозумілу відповідь у форматі JSON. Такий підхід робить API універсальним та запобігає проблемам з відображенням специфічних символів у різних клієнтських додатках, забезпечуючи високу надійність інтерфейсу взаємодії.














4 ВИСНОВКИ
У ході виконання лабораторної роботи було проведено впровадження методів розгортання складних програмних систем за допомогою технологій контейнеризації. Основним результатом роботи стало створення повністю автоматизованої, ізольованої та відтворюваної інфраструктури для системи попереднього замовлення їжі FoodPreOrder, яка об'єднує в собі бекенд-додаток на базі .NET 8, сервер бази даних MS SQL Server та IoT-модуль на базі C++ (PlatformIO).
Важливим висновком роботи є підтвердження ефективності використання Docker Compose як інструменту оркестрації. На практиці було доведено, що декларативний підхід до опису інфраструктури дозволяє значно скоротити час на розгортання системи. Створення єдиного файлу конфігурації docker-compose.yml вирішило проблему сумісності компонентів, забезпечивши їм спільну віртуальну мережу та автоматизоване управління залежностями. Це дозволило API-сервісу звертатися до бази даних за мережевим іменем, що є стандартом побудови сучасних мікросервісних архітектур.
Окрему увагу в роботі було приділено концепції Infrastructure as Code (IaC). Завдяки реалізації автоматичного застосування міграцій у вихідному коді (context.Database.Migrate()), було досягнуто повної автономності системи. Висновок полягає в тому, що інтеграція логіки управління структурою бази даних безпосередньо в життєвий цикл запуску контейнера виключає людський фактор і помилки при розгортанні на нових серверах. Тепер система самостійно готує робоче середовище (створює 16 таблиць та зв'язки), що є критично важливим для хмарних технологій та CI/CD процесів.
Дослідження технології Multi-stage builds у Dockerfile для .NET сервісу дозволило дійти висновку щодо важливості оптимізації образів. Розділення етапів компіляції та виконання не лише зменшило розмір фінального образу, а й підвищило рівень безпеки системи, оскільки середовище виконання (Runtime) не містить вихідного коду або інструментів розробки (SDK). Це робить розгорнуту систему більш захищеною від потенційних атак у промисловому середовищі.
Контейнеризація IoT-модуля на базі PlatformIO та C++ стала підтвердженням універсальності Docker. Використання специфічного образу з встановленим PlatformIO Core дозволило уніфікувати процес компіляції прошивок, незалежно від налаштувань локальної операційної системи розробника. Це вирішує проблему складного управління залежностями вбудованих систем та забезпечує ідентичність збірок на різних етапах розробки.
Загалом, результати лабораторної роботи демонструють, що перехід від локального запуску додатків до контейнеризованого розгортання є необхідним кроком для сучасного інженера-програміста. Створена система є масштабованою, стійкою до змін середовища та готовою до публікації в хмарних сервісах. Отримані навички роботи з Docker, мережами контейнерів та автоматизацією баз даних складають фундамент для подальшої професійної розробки високонавантажених та розподілених систем.
